# Hands-on tests, 2026-10-17 and 2026-10-18 (build 2705.1.30, Windows)

Every line here was run live through the ClaudeJobRunner add-in in scratch documents (job files `cl01` to `cl30`, `v2a` to `v2g`). Numbers are measured, not quoted. Test files went into a scratch cloud folder that was removed afterwards. No customer model was opened for these tests.

## Environment (job cl01)
- `app.version` = `2705.1.30` (the October 5, 2026 release; patch on the September 2026 feature release 2705.1.11).
- At startup with no file open: `app.documents.count` = 0, `app.activeDocument` = None, `ui.activeCommand` = `''` (empty string, not "SelectCommand").
- `app.data` shows the signed-in user, the hub and the active project ("Default Project" on a fresh account).
- Preferences: `generalPreferences.defaultModelingOrientation` = 0 (**Y up**, Fusion's default); default length units for new designs = in; `isAutomaticSaveOnCloseEnabled` = True; `isAutomaticVersioningEnabled` = False; API `debuggingPort` = 9000.
- First new document after a fresh start takes 7 to 13 s; later ones about 1 s.
- Fusion relaunch to runner live: 48 to 113 s (FusionLauncher.exe; the runner writes runner_started.txt). Graceful close with no documents open: WM_CLOSE to the main window, 8 to 46 s.
- Viewport image capture works while Fusion is minimized.

## Pipe feature (cl02, cl07)
- `root.features.pipeFeatures.createInput(path, NewBodyFeatureOperation)` with `sectionType = CircularPipeSectionType`, `sectionSize = OD`, `sectionThickness = wall` (setting thickness also sets `isHollow`).
- **`sectionSize` is the outside DIAMETER**: 4.5 in gave a 4.5 in wide body. Volume check on a 240 + 240 + 60 in path with two 6 in radius sketch fillets: Fusion 1,697.6 in3, hand math 3.174 in2 x 534.85 in = 1,697.6 in3. Exact.
- One pipe feature along a 3-segment path with 2 fillets: 0.63 s, one valid solid, 12 faces.
- Sketch fillets between 3D (non-planar to the sketch) lines work: `sketchArcs.addFillet(l1, l1.endSketchPoint.geometry, l2, l2.startSketchPoint.geometry, r)` succeeded on both corners of a path that leaves the sketch plane.
- `features.createPath(firstLine, True)` chains connected lines and arcs.
- Parameter driven: `design.userParameters.add("CHW_OD", ValueInput.createByString("4.5 in"), "in", "...")` then `sectionSize = ValueInput.createByString("CHW_OD")` works and the feature shows expression `CHW_OD`. `createByReal(cm)` instead stores an expression like `114.30 mm`.

## Temporary B-Rep speed and the torus bug (cl02 to cl06, cl19, cl20)
- 500 solid cylinders 0.04 s; 100 hollow cylinders (outer minus inner with `booleanOperation(..., DifferenceBooleanType)`) 0.12 s; temp body creation is effectively free.
- **BUG: `TemporaryBRepManager.createTorus(center, axis, R, r)` ignores `center`.** The torus is always built at the origin (axis is honored). A quarter-torus elbow made away from the origin by intersecting with a box comes out EMPTY (faces = 0) while `booleanOperation` still returns True. 50 of 50 elbows were empty in cl02. Workaround verified: build the elbow at the origin, then `tbm.transform(body, matrix)`; volume exact (149.89 in3 for R 6 in, r 2.25 in). `createBox` and `createSphere` DO honor their center.
- Adding bodies (3,000 hollow pipes in 30 components, 100 per component):

| Method | Seconds |
|---|---|
| Parametric, one body per pipe, one base feature per component | 214 (14 bodies/s) |
| Direct design, one body per pipe | 91 (33 bodies/s) |
| Parametric, the 100 pipes of each component UNIONED into one temp body first | 35 |
| Direct design, unioned per component | **14** |
| For comparison: STEP import of about 3,200 solids (earlier session) | 36, plus CadQuery time |

- A unioned body of 100 disjoint pipes is accepted as ONE body with 100 lumps (`lumps.count` = 100, `isValid` True, volume exact). So "one body per layer" works natively, no STEP needed.
- 650 bodies into a single base feature in a single component: 6.3 s (adding cost grows with the number of base features and components, not only bodies).

## Whole building piping model built natively (cl25 to cl27)
- Op list from a read-only copy of a Python piping model (`dump_ops.py`): `model.build_all()` about 8 s, about 7,300 ops, about 4,800 kept after the filters (no hangers, insulation, details, gallery, floor plan): mostly cylinders and boxes, plus about 190 elbows, 180 spheres, 170 tori and 20 cones, in about 50 layers.
- `scripts/ops_to_fusion.py ops.json job.py --png ...` then `fjob.py job.py 900`: **42 s in Fusion**: temporary pieces 3.6 s (0 failed, 0 empty: every elbow and ring solid with the origin-torus workaround), pairwise unions per layer 17.1 s (0 union failures), new direct document + one colored body per layer component 5.5 s, camera and 2400 x 1500 PNG about 8 s. The busiest layer bodies held 140 to 230 lumps.
- Renders checked: whole building context (walls, columns, equipment in their layer colors) and a piping close-up (supply green, return orange, drops to equipment, supports), Z up.
- The STEP route for the same model was CadQuery (6 s for about 3,200 solids) plus a 36 s Fusion import, with a 21 MB file and no building context. The native route needs no CadQuery and no STEP and colors each layer as a Fusion appearance.
- The scratch document was closed without saving (the cleanup job closes only unsaved documents and stops at any saved one).

## Views and images (cl02, cl03)
- `vp.saveAsImageFileWithOptions(opts)` with `SaveImageFileOptions.create(path)`, `width`, `height`, `isBackgroundTransparent`, `isAntiAliased`: ok, 1600 x 1000 in about 5 s.

## Closing documents (cl04, cl15 to cl18)
- `doc.close(False)` on an unsaved, modified scratch design closes in about 1 s with NO prompt, even with "save on close" turned on.
- **HANG**: closing a drawing document while `FusionDrawingAutoDimensionEditCommand` is active pinned one CPU core (8.5 s CPU per 10 s), froze the log, and needed a kill. That command starts BY ITSELF about 1 to 2 s after a drawing PDF export finishes (cl17 log: SelectCommand right after `execute`, FusionDrawingAutoDimensionEditCommand 1 s later). Fix verified (cl18): `if ui.activeCommand not in ("SelectCommand", ""): ui.terminateActiveCommand()`, then `close(False)` closes in 1.2 s.
- Closing a drawing also closes the design it references (documents went from 2 to 0).
- After a kill, the next start showed no recovery prompt and no document open.

## Cloud save (cl07, cl08)
- `rootFolder.dataFolders.itemByName(name)` returned None for a missing folder (did not raise, unlike `namedViews.itemByName`); `dataFolders.add(name)` creates it.
- `doc.saveAs(name, folder, description, tag)` returned True in 1.5 s. Right after, `doc.dataFile.isComplete` = False and `dataFile.id` is a LOCAL cache path (`...\<login>\F\_<name>.<guid>.f3d`). Within about 8 s `isComplete` = True and `id` became the cloud lineage URN (`urn:adsk.wipprod:dm.lineage:...`). Wait for `isComplete` before passing the DataFile to anything (drawings need it).

## Automatic drawing by API (cl09 to cl14)
- `adsk.drawing.DrawingManager.get().createDrawingInput(dataFile, AutomaticDrawingCreationMode)`. Defaults read back: content FullAssembly, standard ISO, units mm, sheet A3, landscape, sheets AllLevels, base FromScratch. Set ASME, inch, `DASMESheetSize`, `FirstLevelOnlySheetCreationType`. Global prefs defaults: main and sub assembly sheets on, component sheets on, animation off, auto-dimension on, omit keywords "Bolt,Screw,Nut,Washer".
- `createDrawing(input)` is synchronous: **84 s** for a 3-component model, Fusion frozen meanwhile. It returns an already SAVED cloud DataFile (`.f2d`, `isComplete` True) in the same folder; no document opens.
- Result: 5 ANSI D sheets. Sheet 1: isometric of the assembly, balloons 1 to 3, PARTS LIST (item, qty, part number, material). Sheet 2: orthographic views with overall dimensions (120, 264, 36, 122.25). Sheets 3 to 5: one per component with views, center lines and auto dimensions (pipe spool: 240, 90, 242.25, 92.25, diameter 4.5). Title block filled automatically: project name, design name, DRAWN = Autodesk user name, date, scale, sheet n/N, size.
- Part numbers default to creation timestamps ("2026-10-17-20-15-09-881") and material to "Steel": set `component.partNumber`, description and physical material before creating the drawing.
- The date in the title block was the next day's date for an evening run (local time behind UTC): it looks like the UTC date.
- Opening the drawing: `app.documents.open(df, True)` 16 to 47 s (first drawing open after a restart is slowest). Then `adsk.drawing.Drawing.cast(app.activeProduct)` works. `doc.products.itemByProductType("DrawingProductType")` RAISES "failed to find product", and `product.productType` raises InternalValidationError on the drawing product: use `app.activeProduct`.
- `Sheet.width`/`height` read 863.6 x 558.8 (millimeters) on an inch ASME D sheet. Sketch points and image positions are in drawing units (inches here).
- `Sheets.add(input)` puts the new sheet right AFTER the active sheet (it became sheet 2 of 6, not the last).
- `BendTables` has no `count` attribute (AttributeError); `customTables.count` works.
- **`CustomTable.setCellData(row, col, text)` returned False for every index tried (0 to 4, -1) and cells stayed empty.** The table itself is created (top-right corner by default). Schedules cannot be filled by API in this build.
- `Images.insert` works (position in drawing units, `scale` 1.0 made a 1200 px PNG about 2.6 in wide). `DrawingSketch` circles and rectangles work.
- PDF export (`exportManager.createPDFExportOptions(path)`, `openPDF = False`, `useLineWeights = True`, `execute`): 3.5 s, vector, 34 x 22 in pages, producer "pdfplot18.hdi", creator "Fusion Drawings (26.0)".
- DWG export (`createDWGExportOptions`, format 1): 0.3 s, 247 KB. Converted headless with accoreconsole (DXFOUT): AutoCAD 2018 format (AC1032), INSUNITS inches, one LAYOUT per sheet named after the sheet, real DIMENSION entities, MULTILEADER balloons, the parts list as ACAD_TABLE, DRAWINGVIEW entities with VIEWPORTs, model space holds 12 ACDBVIEWREPBLOCKREFERENCE. 40 layers: Visible, Visible Narrow, Hidden, Hidden Narrow, Section Lines, FD_Dimensions, Notes, Leaders, Balloons, Parts Lists, Custom Tables, Titleblock, Border, Smart Centers, Hatching, View Labels and others. So the DWG is a sound base for adding tags and notes with AutoCAD.

## Fusion MCP server turned on (2026-10-18; jobs cl29, cl30, mcp_probe.py)
- Before: `Options.Get MCPServerEnabled` -> OFF; `MCP.Server` -> not running; `MCP.ExecuteScript` -> "Execute script tool is disabled". `Options.List /full` shows ids `MCPServerEnabled` (Bool, username "Fusion MCP Server (runs locally on this device)") and `MCPServerPort` (Int32, 27182).
- `Options.Set MCPServerEnabled ON` -> "changed value from OFF to ON"; `Options.Save` -> saved `NMachineSpecificOptions.xml`; the server started at once ("MCP server is running at http://127.0.0.1:27182/mcp"), listening on 127.0.0.1:27182 only.
- Raw Streamable HTTP from Python (`scripts/mcp_probe.py`): `initialize` returned serverInfo "MCP Server Adapter" 1.0.0, protocol 2025-06-18 and an `Mcp-Session-Id`; `tools/list` returned 4 tools: fusion_mcp_electronics_read, fusion_mcp_execute, fusion_mcp_read, fusion_mcp_update.
- `fusion_mcp_execute` with `{"featureType": "script", "object": {"readOnly": true, "script": ...}}` and NO document open returned `{"message": "version 2705.1.30 docs 0", "success": true}`. A non-read-only script created a document, added a 1 in radius x 10 in cylinder (31.416 in3), closed it and printed "closed True docs 0". So the "script tool is disabled" flag does not block outside clients.
- `claude mcp add --scope user --transport http autodesk-fusion http://127.0.0.1:27182/mcp` -> "Added HTTP MCP server ... to user config"; `claude mcp list` -> "autodesk-fusion: http://127.0.0.1:27182/mcp (HTTP) - Connected". Back up your Claude Code user config before the change.
- Restart test: graceful close (9 s, port closed), relaunch (runner live at +28 s), port 27182 listening again, handshake and `claude mcp list` Connected again. The setting persists.
